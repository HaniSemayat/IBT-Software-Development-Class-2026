## Exercise 1 — Route table

The table describes the routes implemented in the Addis Eats capstone after the Day57 changes.

| Method | Path | Purpose | Success | Possible failures |
|---|---|---|---|---|
| GET | `/api/v1/restaurants` | List, filter, sort and paginate restaurants | 200 | 400, 422, 500 |
| GET | `/api/v1/restaurants/{id}` | Retrieve one restaurant | 200 | 404, 500 |
| GET | `/api/v1/restaurants/{id}/menu` | Retrieve a restaurant's menu | 200 | 404, 500 |
| POST | `/api/v1/orders` | Create an order | 201 | 400, 404, 422, 500 |
| GET | `/api/v1/orders/{id}` | Retrieve one order | 200 | 404, 500 |
| PATCH | `/api/v1/orders/{id}/status` | Change an order's status | 204 | 400, 404, 409, 500 |

**Status-code notes:**

- `200 OK`: A read succeeded and returns a representation.
- `201 Created`: An order was created. The response includes the created resource and a `Location` header generated by `CreatedAtAction`.
- `204 No Content`: The order status was updated successfully. There is deliberately no response body.
- `400 Bad Request`: Invalid input, malformed values, or unsupported query parameters.
- `404 Not Found`: The requested restaurant or order does not exist.
- `409 Conflict`: The requested operation conflicts with the current state of an order.
- `422 Unprocessable Content`: The request was understood, but its business meaning is invalid.
- `500 Internal Server Error`: An unexpected server-side failure. It is not used for ordinary invalid input.

The API does not currently implement authentication, order deletion, or payment processing. Those are not listed as working routes.

## Exercise 2 — Identifiers versus filters

| Path or parameter | Classification | Decision |
|---|---|---|
| `/api/v1` | API version | Keep in the path |
| `/restaurants` | Collection resource | Keep in the path |
| `/restaurants/{id}` | Identifier | Keep in the path |
| `/restaurants/{id}/menu` | Related resource | Keep as a one-level nested path |
| `/orders` | Collection resource | Keep in the path |
| `/orders/{id}` | Identifier | Keep in the path |
| `/orders/{id}/status` | Related state resource | Keep as a one-level nested path |
| `?area=Bole` | Filter | Keep in the query string |
| `?areas=Bole&areas=Piassa` | Multiple filter values | Keep repeated query keys |
| `?maxFeeEtb=60` | Numeric filter | Keep in the query string |
| `?page=2&limit=20` | Pagination | Keep in the query string |
| `?sort=-deliveryFeeEtb` | Sorting | Keep in the query string |

An identifier selects one particular resource, so it belongs in the path. A filter changes the subset returned by a collection endpoint, so it belongs in the query string.

The current API keeps nesting to two resource levels after the version prefix. The restaurant menu is a reasonable nested resource because it belongs to a restaurant.

## Exercise 3 — Verbs in paths

The current capstone paths do not contain action verbs such as `get`, `create`, `update`, or `delete`. The HTTP method already expresses the operation.

For the order-cancellation example, the three designs taught in class are:

| Approach | Design | Evaluation |
|---|---|---|
| State change | `PATCH /api/v1/orders/91/status` with `{"status":"Cancelled"}` | Preferred: cancellation is a change in order state |
| Event resource | `POST /api/v1/orders/91/cancellations` | Appropriate if cancellation reasons and timestamps must be stored as separate resources |
| Named action | `POST /api/v1/orders/91/cancel` | Acceptable only when the operation cannot be represented cleanly as a resource change |

**Choice:** I would use `PATCH /api/v1/orders/91/status`. It is consistent with the existing order-status resource, clearly communicates a partial update, and avoids putting an action verb in the path.

## Exercise 4 — Error catalogue

| Machine code | HTTP status | Situation | Client-facing message |
|---|---:|---|---|
| `VALIDATION_FAILED` | 400 | Missing, malformed, or invalid request field | One or more request values are invalid. |
| `UNKNOWN_QUERY_PARAMETER` | 400 | Unsupported query parameter | The request contains an unsupported query parameter. |
| `RESTAURANT_NOT_FOUND` | 404 | Restaurant ID does not exist | The requested restaurant was not found. |
| `ORDER_NOT_FOUND` | 404 | Order ID does not exist | The requested order was not found. |
| `RESTAURANT_CLOSED` | 409 | An order conflicts with restaurant availability | This restaurant is currently closed. |
| `ORDER_ALREADY_DELIVERED` | 409 | Attempt to cancel a delivered order | A delivered order cannot be cancelled. |
| `AMOUNT_INVALID` | 422 | Negative or zero business amount | The amount must be greater than zero. |
| `PAYMENT_DECLINED` | 402 | Payment provider declines a charge | The payment was declined. |
| `INTERNAL_ERROR` | 500 | Unexpected server-side failure | Something went wrong. Please try again later. |

The error code is intended for application logic. The title and detail are intended for people. Clients should not need to parse a sentence to determine what happened.

The capstone uses a consistent ProblemDetails-style response containing `type`, `title`, `status`, `detail`, `instance`, and a machine-readable `code`. Validation errors can additionally include an `errors` object.

## Exercise 5 — Choose the correct status code

**1. A restaurant search returns no rows.**

`200 OK`, with an empty collection in the response. The request succeeded; no matching resources were found. A 404 would incorrectly suggest that the endpoint itself does not exist.

**2. A customer tries to cancel an already-delivered order.**

`409 Conflict`. The request is understood, but it conflicts with the current state of the order. A delivered order cannot transition to Cancelled.

**3. A submitted order total is negative ETB.**

`422 Unprocessable Content`. The request can be parsed, but the amount violates a business rule. It is not an unexpected server error.

**4. A courier with a valid token tries to edit a restaurant menu.**

`403 Forbidden`. The caller is authenticated, but does not have permission to perform that operation. A 401 would mean the caller has not successfully authenticated.

## Exercise 6 — Review of twelve badly designed routes

**Important note:** The twelve original routes mentioned in the classroom instructions were not included in the supplied 30-slide presentation. The following is a representative practice set based on the exact naming conventions in the slides. It is not claimed to be the instructor's original handout.

| Bad route | Better design | Naming rule violated |
|---|---|---|
| `GET /getRestaurants` | `GET /restaurants` | Verb in path; camelCase |
| `GET /restaurant` | `GET /restaurants` | Singular collection |
| `POST /createOrder` | `POST /orders` | Verb in path |
| `GET /getRestaurantById?id=14` | `GET /restaurants/14` | Verb in path; identifier in query |
| `GET /listBoleRestaurants` | `GET /restaurants?area=Bole` | Verb in path; filter in path |
| `POST /updateOrderStatus?id=91` | `PATCH /orders/91/status` | Verb in path; identifier in query; wrong method |
| `GET /MenuItems` | `GET /menu-items` | Uppercase and inconsistent naming |
| `GET /menu_items` | `GET /menu-items` | Underscore instead of hyphen |
| `GET /orders/91.json` | `GET /orders/91` | File extension in path |
| `GET /restaurants/14/` | `GET /restaurants/14` | Trailing slash |
| `GET /restaurants/14/menu/7/reviews/3` | `GET /reviews/3` or `GET /reviews?menuItemId=7` | Excessive nesting |
| `GET /restaurants/area/Bole` | `GET /restaurants?area=Bole` | Filter incorrectly placed in path |

The improved paths use plural resource collections, nouns rather than action verbs, lowercase hyphenated names, identifiers in the path, filters in the query, and no unnecessary nesting.

## Exercise 7 — REST, GraphQL or gRPC?

**1. Public mobile API — REST**

I would choose REST because it uses standard HTTP methods and status codes, is easy to test and cache, and is widely supported by mobile clients. Its predictable resource URLs make it straightforward for a public API.

**2. Internal service-to-service communication — gRPC**

I would choose gRPC because it uses Protocol Buffers and generated clients to provide strongly typed contracts between services. Its efficient binary messages and HTTP/2 support make it suitable for high-performance internal communication.

**3. Dashboard that needs six resources on one screen — GraphQL**

I would choose GraphQL because the dashboard can request the exact fields and related resources it needs in one query. This can reduce multiple REST round trips and avoid fetching large amounts of unused data.

## Exercise 8 — Unknown query parameters

**Decision: Reject unknown query parameters with HTTP 400.**

For example:

`GET /api/v1/restaurants?arrea=Bole`

This request contains a likely spelling mistake. Silently ignoring `arrea` could return every restaurant and make the client believe the filter worked.

The restaurant collection currently accepts:

- `area`
- `areas` (repeat the key for multiple values)
- `maxFeeEtb`
- `page`
- `limit`
- `sort`

Unsupported parameters return a ProblemDetails-style error with code `UNKNOWN_QUERY_PARAMETER`.

Pagination uses offset paging because the restaurant collection is small and users may need numbered pages. The default page is 1, the default limit is 20, and the maximum limit is 100. Requests above the maximum are capped at 100.

Supported sort fields are `name`, `-name`, `deliveryFeeEtb`, and `-deliveryFeeEtb`. A leading minus means descending order. Unsupported sort fields are rejected.

## Capstone design decisions

- API versioning: URL path versioning with `/api/v1`.
- Resource naming: plural, lowercase nouns.
- Identifiers: path parameters.
- Filters and pagination: query parameters.
- Nested resources: no more than two resource levels.
- GET: read resources and return 200.
- POST: create resources and return 201 with a Location header.
- PATCH: update part of a resource and return 204 when no representation is returned.
- Errors: consistent ProblemDetails-style response with a machine-readable code.
- Unknown query parameters: reject with 400.
- Pagination: offset-based with a maximum limit of 100.
- Sorting: whitelist accepted sort fields.
